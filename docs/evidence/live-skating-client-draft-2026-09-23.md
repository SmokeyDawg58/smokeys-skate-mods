# Controlled native skating window draft — 2026-09-23

Unregistered review packet: `apps/skate2-pc/src/live_skating_client_draft_20260923.rs` and `artifacts/live-skating-full-client-2026-09-23-draft.patch`. The patch adds `--live-skating` on Windows, a diagnostic window title, and Windows-target `rustix 1.1.4` with `net` for the existing unregistered `windows_juice_platform.rs` adapter. It consumes the now-registered `SelectedLiveSession` public facade and `LiveSkatingView`; it does not implement another archive, map, input, simulation, camera, material or GPU owner. `git apply --check` and `rustfmt --check` pass. No registered file or Cargo was changed by this author. The packet needs independent review, root compilation and a real Windows original-data/GPU run.

The client mounts original archives once, passes the same `Arc<MountSet>` to `Inspection::load` and `SelectedLiveSession::new`, reads external `Juice_m.ini`, and supplies an explicit **controlled first-test profile** to `try_begin_controlled`. The facade resolves `SelectedSpawnPolicy::AuthoredSelectedLocation` and `SelectedGravityPolicy::VaultSkateboardDefault` from its retained `SelectedOriginalAssets`; the app does not parse a second location table or load another Vault. It uses the debug reference camera-set seed, default marquee, original mounted A_RobsPark collection `823c4449fb3163b4`, single-player physics flags3, graph allocation, authored terrain start, selected palette policy and native-static command fields. These are explicit host selections, not reconstructed automatic spawn/registration scheduling. The app's `RootW` opaque-zero transport is exactly the current passing original-data corpus's first-test policy; source W production is unresolved. The source assertion/hat callbacks fail loudly if an unsupported branch is reached. The hands-clamp callback returns a typed error if called.

`WindowsPadPlatform` is passed directly into the same core input owner; `SelectedLiveSession::try_tick` performs hardware poll/cache, preupdate enqueue, Actor, physics, selected camera and presentation. Window focus is forwarded as a host input gate. The app schedules those selected ticks at a fixed host 1/60 clock independent of redraw cadence, without silently dropping catch-up ticks. On `Completed`, it immediately borrows `try_visual_snapshot()` and updates the static map plus selected character objects through the registered `LiveSkatingView` using that snapshot's provisional CameraMan clip and same-frame palette/materials. On `NoCommands`, it retains the last displayed objects and logs the lack of a simulation command. There is no keyboard-to-pad mapping in this draft; the first interaction target is a Windows XInput gamepad. No claim of native timer/network/Flow cadence, exact Xenon physics numerics, source camera restore/interpolation, dynamic presentation streaming or enabled PROXY kind0/2/10 activation is made. The title/log labels the controlled test, static original map, diagnostic shading and provisional camera.

`windows_juice_platform.rs` uses `rustix::net::wsa_startup` and `wsa_cleanup`, which are safe public Windows APIs in the locally pinned rustix 1.1.4 `net` module; this maps PC Winsock/TcpStream to the host Juice service and does not claim Xbox XNet parity. `JuiceHostOption::DisableBeforeStart` remains an explicit first-test choice. The app's animation-thread answer hashes the current Rust `ThreadId` into a process-local `u64` because stable Rust does not expose a numeric `ThreadId` and the startup owner currently only retains the answer; this is not a native OS/Xbox thread ID. If that field gains an operational consumer, it needs a reviewed platform thread-id source.

Validation after integration should run app/workspace compile and formatting, the mounted selected original-data corpus, then `SKATE2_GAME_ROOT=... skate2-pc --live-skating` on Windows with a controller and compatible GPU. The first visual run may expose a typed camera-W, material/texture, cloth, renderer or stream failure; such a failure is the next source/consumer gate, not a reason to substitute geometry or a camera. The existing `--render-inspection` command and diagnostics remain separate.

Reviewer corrections: The live command no longer calls the app's verify_world_stream_probe_identity helper because it would parse BAM_Sim locations again; the facade retains the original selected spawn. Initial window focus is false until an observed WindowEvent::Focused value, so startup cannot invent a focus-gain command. can_simulate=true remains an explicit controlled host fixture, not recovered native scheduling.
