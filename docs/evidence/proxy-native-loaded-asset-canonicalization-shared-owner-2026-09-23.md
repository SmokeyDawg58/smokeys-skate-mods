# PROXY loaded-asset canonicalization and unified Presentation owner (2026-09-23)

Read-only IDA and registered Rust audit. The exact new path was absent before writing. No registered source, Cargo command, parser, or uploader was changed. Confidence is **exact** for the cited native branches, **high** for the resulting shared-identity chain within one `cAssetManager`, and **high** for the current Rust ownership gap. This is a bounded shared-owner proof packet, not enabled PROXY registration.

## Native identity chain

`cAssetStreamer::Update` (`0x82d61154..0x82d61234`) has a loaded-*collection* map keyed by full collection ID. A repeated load of that collection increments its resident count and reuses its `cCollection`; a new collection allocates its own ordered vector. On physical completion, the streamer publishes the collection wrapper to `mContainerAssetRegistry` at `0x82d60fc8..0x82d61024`, then invokes its load callback at `0x82d6102c..4c`. The Presentation registration and deregistration receivers each resolve that container by full collection ID (`0x827809e4`, `0x82780078`) and walk the stored asset pointers forward. `cAssetRegistry::GetRegAsset` (`0x82d62980`) is a lookup; `AddRegAsset` (`0x82d64890`) inserts only if the key is absent. The container registry alone does not explain same-arena identity across *different* collections.

The canonicalizing step is `cAssetManager::AddCompressedArenaAsset` (`0x82d63a10`), reached from `cAssetStreamer::DecompressThread` (`0x82d5b008`) for compressed arena entries. Under its add/loaded-map locks it searches `mLoadedAssetMap` by the **full asset ID** at `0x82d63a70..90`. A hit returns the existing processed `cAsset*` and increments its loaded count at `0x82d63bc8..bd0`, bypassing `CreateCompressedArenaAssetData` (`0x82d63abc`) and the `ProcessAsset` call (`0x82d63b1c`). A miss creates/processes once, then inserts that pointer with count one (`0x82d63b30..bac`). The ordinary `AddAsset` variant (`0x82d636a0`) and other compressed variants have the same loaded-map lookup/reuse shape. `tLoadCollectionRequest::EntryComplete` appends the returned pointer to its collection at `0x82d5e530`. Thus two live collections that load arena ID X through the same manager contain pointers to **one** processed arena allocation, including its kind-0 alias, even though their collection vectors are distinct.

`cAssetManager::DownLoadedCount` (`0x82d62e78`) decrements that full-ID loaded count (`0x82d62edc..e0`) and only on zero unprocesses/frees and erases the loaded-map row (`0x82d62efc..0x82d62fac`). `cAssetStreamer::DownCollectionLoadedCount` (`0x82d57de0`) first waits for the collection's resident count to reach zero, then walks its asset pointers and calls the manager's per-asset down operation (`0x82d57e64..eec`), removes the container registry wrapper (`0x82d57f04..10`), and destroys that collection. The Presentation first/last-use counter, asset-manager loaded count, and collection resident count are three different counters.

For shared arena ID X: A's physical load creates processed arena P (asset loaded count one); B's load reuses P (count two). A's first Presentation `AddAsset(X)` runs `RegArena(P)` and kind-0 `AddTexture(P.alias, toc_id)`. B's `AddAsset(X)` is retained use and does not add again. If A's Presentation deregistration runs first, it is retained use and A's later physical unload decrements P's loaded count to one. B's last-use deregistration still visits **P**, so `DRegArena(P)` passes the same alias pointer to `RemTexture`; B's final physical unload can then take P to zero. This corrects the hypothetical different-pointer scenario in the earlier standalone-effect withdrawal. It does **not** make that withdrawn host effect safe: the current host builder creates separate boxed aliases for equal IDs in different resident collections and has no corresponding loaded-asset map.

## Registered Rust and unregistered producer audit

`CollectionResidentStreamer` already coalesces repeated loads of one collection ID, and `CatalogResidentCollectionLoadFactory` plus `MountedResidentCollectionLoadDriver` feed real mounted bytes through `DecodedArenaAssetBuilder` into `OwnedResidentCollectionStorage`. The storage retains each collection's assets in authored order but has no cross-collection full-asset-ID canonicalization. `OwnedResidentAssetsView::try_for_each` borrows those values only for one visit. The unregistered `proxy_kind0_resident_builder_draft_20260923.rs` uses that decoder, the existing `own_texture_arena` parser, and the proposed renderer-backed uploader; it accepts only the selected parent collection and creates a fresh `Box<Kind0AliasProduct>` per build. The separate unregistered `proxy_texture_resident_client_draft.rs` also uploads a selected texture but does not publish a native alias. Neither is a shared loaded-asset owner. The existing `proxy_shader_texture_table_draft.rs` models shader slots only and is not registered.

For kind 2, `own_presentation_arena` already decodes material/geometry inventories and `PresentationDmoArenaRegistrationAdapter` has a checked whole-material source handle and ordered material dispatch **only for its main-DMO-bank slice**. Neither executes PROXY `TextureMan::AddMaterial`'s mutable channel stream resolution, configured missing-texture fallback, and registry/slot lookup order. For kind 10, the Simulation Environment unlock/router and source admission proofs exist, while PROXY Presentation `PresUnlockableLocationMan::AddToWorld` → `WorldPresentation::AddRenderInstance` is not a connected retained consumer. The observed PROXY producer map has parent/spatial kind 0, spatial kind 2, and conditionally admitted kind 10; these effects share the native Presentation arena traversal. No registered app owner currently composes all three. Reusing the format parser, load driver, `own_texture_arena`, material source decoding, and GPU uploader avoids another asset inventory.

## Bounded owner and caller contract

The next physical asset seam is one loaded-asset map in the existing resident-load composition, keyed by full arena ID for the same manager domain. On a miss, run the existing decoded builder and appropriate processed kind-0/2/10 producer once, retaining a single owner-bound processed arena allocation. On a hit, append a handle to that **same** allocation to the new collection without another parse/upload. A collection row remains ordered and may contain duplicate handles. The loaded-asset map retains or counts the physical uses and releases the processed allocation only after each collection's corresponding asset down; it must not be the Presentation registration counter. The current boxed kind-0 product must be wrapped with its decoded source in one shared allocation before this can work. A narrow wrapper implementing `ResidentAssetIdentity` can let `OwnedResidentCollection` retain handles to that same allocation; no second stream driver or parser is required.

One Presentation owner then owns **one** `ArenaRegistrationRefCounter` for all admitted kinds, the existing shader table, a processed-container lookup/ordered occurrence record, and the real kind-2 and kind-10 dispatch collaborators. It takes an already retained collection from the streamer, resolves its shared processed arena handles, and visits each arena and its processed products in source order. `FirstUse` invokes the kind-0/2/10 effects appropriate to that arena; retained use only increments the counter. `LastUse` runs the paired deregistration over the **same canonical processed allocation**. The `PresentationDmoArenaRegistrationAdapter` already proves how a live occurrence and first-use owner are retained around a first/last-use gate, but its private counter and bank-specific dispatch cannot be instantiated as a parallel proxy Presentation namespace. A unified owner must refactor or integrate that decision boundary if both paths can coexist.

The caller order is concrete: physical collection completion publishes its container **before** invoking the parent load callback; first parent use raises the Simulation resident hold, sends Simulation registration, raises the separate Presentation hold, then sends Presentation registration. The Presentation receiver completes all ordered first-use effects before its separately queued parent load callback runs; that callback does not lower the hold. After the required parent and spatial physical collections load, `SyncActivateProxyWorld` (`0x824d9ef8`) enqueues an activating Presentation registration message, then a separate activation callback message for each sorted collection (`0x824d9f88..0x824da080`). Only those callbacks increment activated count. At parent last use, Simulation and Presentation deregistration are sent separately; the Presentation receiver performs last-use removals before its unload callback releases that resident hold. `CollectionParentEffects` currently exposes delivery `Result<()>` by collection ID, not a processed-container/live-occurrence authority or asynchronous callback completion. A host caller must bind those authorities and must not interpret message delivery or a census as activation.

Focused proof before registration: two different resident collections containing the same full arena ID must produce one decoded/processed allocation and one GPU upload, expose pointer-equal processed handles, increment/decrement the physical loaded count independently, and give the same alias identity to first-use `AddTexture` and last-use `RemTexture`. A same-low-word/different-high-word pair must remain distinct. Verify authored arena and processed-product order, callback after all effects, and no callback or hold release after a prefix error. Then check the actual mounted PROXY parent/spatial corpus and the kind-2/10 producer effects. This packet does not implement those owners or claim first-skater PROXY activation.
