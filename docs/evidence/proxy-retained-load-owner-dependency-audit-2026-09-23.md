# Retained PROXY load-owner dependency audit (2026-09-23)

Read-only design boundary for the first enabled-PROXY production edge. `proxy_asset_census.rs`, `SelectedWorldStream`, the Rob's Park parent-expanded resident probe, and native `cProxyWorldManager::SyncLoadProxyWorldStream`/callbacks were inspected. The exact evidence path was absent before writing. No registered source, Cargo command, or activation draft was changed. Confidence is exact for cited PPC branches and current Rust API behavior; XSS sort-key construction is unresolved.

Native `GameModule::OneOffLoad8273add8` calls the retained `cAssetStreamSystem`/`cProxyWorldManager` PROXY load and activation before normal BAM start (`proxy-world-boot-order-2026-09-23.md`). `SyncLoadProxyWorldStream824df648` loads the Presentation PROXY stream, waits for its metadata, reads the XSS, builds 16-byte `tProxySort` rows, calls `eastl::merge_sort_buffer` at `824dfa14`, then, for each sorted row, inserts its ID into `mProxyCollectionMap`, calls `LoadCollection` with `mLoadProxyWorldRequestCallback`, and retains the ID (`824dfa64..88`). It waits for `mCollectionsLoaded == mNumProxyCollections` at `824dfab8..fac0`. Fresh PPC at `ProxyCollectionOrderCompare824d6888` loads signed 32-bit `mOrder` at offset +8 and returns only strict `<` (`cmpw`/`blt`); equal-key behavior still depends on the called merge implementation. The sort key is computed through floor/coordinate operations at `824df890..9d0`, ending in `mOrder = second_cell/10 + 10000 * first_cell` at `824df9d0`; its vector constants and complete coordinate transform are not yet recovered, so sorting by authored XSS order, collection ID, or generic distance is unjustified. Fresh `cLoadProxyWorldRequestCallback::OnComplete824d68a8` ignores its ID and increments the manager's `mCollectionsLoaded` word at +0x28 (`824d68ac..b4`). This callback count is distinct from resident cache count, parent use count, and activation count.

The existing `CollectionParentManager::plan_load` already expands each spatial request ancestor-first. The PROXY corpus has 147 XSS spatial requests, 127 with the one 93-asset global parent and 20 terminal rows (`proxy-parent-asset-producer-audit-2026-09-23.md`); these are fixture observations, not native constants. The existing `CatalogResidentCollectionLoadFactory`, `CollectionResidentStreamer`, and `OwnedResidentCollectionStorage` can physically load and retain decoded assets. The Rob's Park probe proves a parent-expanded use of those exact collaborators, but its `ProbeParentEffects` records events instead of applying game effects. The PROXY census directly drives 148 unique collection loads in first-seen authored order and never delivers parent or spatial callbacks. Neither is an enabled boot owner.

The first-use parent callback is an effectful gate, not bookkeeping that may be deferred until later activation. `LoadParentCollectionCallback::complete_with` (`collection_parent_manager.rs:294`) increments the parent's use count, then on first use calls active resident `Up`, `simulation_register`, another `Up`, and `presentation_register`, in that order; a failed effect returns an error with its partial prefix. The 127 later parent uses do not resend registration. In the current Rust tree there is no PROXY Presentation resident registry/processed product owner, no actual kind-0/2/10 registration dispatcher, and no concrete `CollectionParentEffects` implementation that can deliver the first parent Presentation registration. `SimulationResidentRegistry<A>` has a generic physical wrapper implementation, but it is the Simulation namespace and its published arena lookup/selected processor contracts are not a PROXY Presentation owner. Reusing it as if it were Presentation would confuse source identity and effect ownership. The child spatial load callback must increment the **same** retained proxy manager's loaded count only after its resident completion; a mere queued request or decoded count cannot do so.

A minimal correct owner would retain **one** PROXY stream registration/catalog, one `CollectionParentManager`, one resident streamer/storage/registry, sorted XSS IDs, `mProxyCollectionMap` membership, and separate loaded/activated counters. Its load request callback would be passed only for the spatial leaf of each parent plan, while the ancestor receives `load_parent_callback()`. The parent manager must receive real Simulation and Presentation registration effects supplied by the retained boot composition; no success-only observation adapter qualifies. The owner may report `Loaded` only after all 147 spatial callback completions and must leave `Activated` pending until source-ordered processed kind-0/2/admitted-10 Presentation effects and their separate activation callbacks run. BAM `SelectedWorldStream` can then receive the same completed owner for high-collection membership. The later renderer consumes that same resident asset namespace and does not build a second `TextureScene` or upload-only owner.

I did **not** draft Rust for this edge because two implementation inputs remain unproven: the exact native `tProxySort::mOrder` transform, and the concrete first-use parent Presentation registration service. A generic injected trait that returns success would make the wait appear complete while postponing effects the native parent callback already performed. The next focused source step is recover the sort-key vector constants/input transform and compare the resulting 147-ID order against the original XSS; the next production step is the source-ordered processed Presentation arena/registry path for the 93 parent Texture products, with actual kind-0 first-use effects. Only then is a load-owner draft able to deliver real callbacks without fake completion. The independent upload-client review remains at `artifacts/proxy-texture-resident-client-independent-review-2026-09-23.md`; that unregistered client is not this owner.
