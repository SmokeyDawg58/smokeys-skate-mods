# Register request before Actor: selected mounted split — 2026-09-23

The integrated `SelectedPlayerStartup::try_prepare_mounted_registration` retains the selected recipe, loader, world identity, and global animation owners, and returns the actual `CharacterRegistrationRequest` before `try_initialize` constructs Actor. The existing `try_initialize_mounted` calls that prefix and then `try_initialize`, preserving its corpus behavior. **Register is a request, not a completion status.** Root integrated the independently reviewed split and reported `cargo check --workspace` passing. The review patch remains at `artifacts/selected-player-registration-before-actor-split-2026-09-23.patch`.

This split changes no recipe parser, Actor constructor, physical constructor, or existing caller. It marks `mounted_attempted` before fallible work, so partial writes remain in a caller-owned `SelectedPlayerStartup`. `SelectedSessionPlayerStartup::try_new_inner` still creates that owner locally and discards it on error. A retained session integration should construct and hold the selected/source pair before invoking the prefix and should retain the returned request rather than discarding it as the legacy wrapper does.

## Direct IDA order and corrected dependency

`PlayerLoaderImpl::OnSimCharacterLoaded 0x82817f28` applies attributes; `SimCharacterManager::Register 0x82817a08` reserves a request. `PresCharacterManager::ReceiveSimRegisterCharacterRequest 0x8281bab8` calls `CharacterRecipeLoader::Register 0x82cfd418`; its notification reaches `PresThreadMsgMan::ReceiveRegSchemaMsg 0x8277c318`, `SkaterPresentation::RegRecipe 0x827e6198`, and the recipe map. Those calls **do not** create the ordinary skater presentation entity.

The ordinary `SkaterPresEntity` is allocated by `SkaterPresentation::UpdatePresEntity 0x827e62cc` and constructed at `0x827e6310`, after a recipe-map lookup and valid character LOD checks. Its only direct code caller is `SkaterPresentation::DoSimRestore 0x827e69f8`, which consumes skater DataSystem records. `SkaterPresentation::DoSimSubmit 0x827dd2e8` builds those records from `SkaterManager::GetActor` / `ISubmittableSkater` (plus an optional playback skater). `GetSkaterPresEntity 0x827d3328` searches the resulting model array. The other direct constructor callers are scene/NIS, CAC, and viewer paths; none is established as the first ordinary local skater producer.

`PresCharacterManager::Update 0x82818f2c..82818f94` emits `LoadStatus_Registration` only when the searched entity exists and its peer matches the loader's registered peer. `SimCharacterManager::ReceiveLoadStatusMessage 0x82816c10` dispatches `SimCharacterRequest::OnRegistered 0x82815528` to `PlayerLoaderImpl::OnSimCharacterRegistered 0x82818098`; that callback clears the matching request and creates no Actor. For the first ordinary player, requiring this completion **before** Actor would form a cycle with the observed Actor submit/restore producer. The earlier pre-Actor-completion design in this packet is withdrawn.

`PlayerUI::ReceiveSpawnMsg 0x828ac8b0` checks its location spawner, gets a spawn transform, and dispatches command 3; `SkaterManager::OnCommand 0x82600920` then calls `SpawnPlayer 0x82600630`, whose Actor constructor includes the physical pair before roster/entity publication and `InitPlayer 0x826000b0`. `GameModule::ResetGame 0x8273ab5c` supplies `SK8App->mLocationMan` as the UI spawner. The receiver's virtual `IsSpawnerReady` call uses vtable slot `+0xC`; `cLocationManager` vtable `0x82252b98` points that slot at `0x826c6d80`, a trivial function returning true. The symbol at that COMDAT body is misleadingly named `ICESceneBridge::IsCameraUsingSceneUp`. Thus this receiver does not check registration completion. **The producer and timing of the `cMsgSpawnPlayer` message remain untraced**; the binary evidence does not prove that Actor always precedes completion, only that a completion-before-Actor requirement is unsupported and appears cyclic for the observed ordinary path.

## Concrete producer path still needed

1. Retain the exact returned `CharacterRegistrationRequest` and the same mounted recipe occurrence. Implement presentation recipe-map registration and a pending request owner without marking the loader complete.
2. Accept a source-justified spawn command or explicit host-selected first-test spawn, then construct one Actor/physical pair and publish it to the same skater/entity roster. Avoid a fictitious pre-Actor completion receipt.
3. Submit the Actor's real `ISubmittableSkater` data, restore it through the selected presentation owner, and construct the ordinary `SkaterPresEntity` from the registered recipe and the submitted peer. The existing `try_initialize_mounted_presentation` initializes retained animation/resources but does not itself publish this live entity or data.
4. On presentation update, look up the actual entity by character/recipe ID and compare its peer with the pending loader peer. Only that match emits a typed Registration status. Deliver the status to the matching simulation request; then call `PlayerLoaderSlot::character_registered(request_id, character_id)` and retain its `Complete` result. Missing entity, wrong peer, stale request and failed presentation construction cannot complete the loader.

Rust already has the Register request, `PlayerLoaderSlot::character_registered`, mounted recipe/scene owners, Actor/physical pair constructors and selected presentation startup. It lacks the production recipe-map notification/queue, ordinary presentation entity/peer roster, live submit/restore admission, peer-gated status delivery, and exact spawn-message scheduling. These are the concrete remaining services. The split provides a useful request boundary, but neither the boot draft nor a host callback may claim that it produced registration completion.
