## Native root and callback boundary

`GameModule::OneOffLoad` (`0x8273add8`) initializes Simulation (`0x8273b120`) and Presentation (`0x8273b15c`) before loading PROXY. It reads the live proxy cvar at `0x8273b41c/420`, calls retained `cAssetStreamSystem::SyncLoadProxyWorldStream` at `0x8273b474` when enabled, reads the cvar again at `0x8273b490/494`, calls `SyncActivateProxyWorld` at `0x8273b4e0` when enabled, and only then starts the ordinary `worldFile` stream at `0x8273b524`. This is the `cGameAssetManager`/asset-stream-system composition seam, before `SelectedWorldStream` should start BAM.

`cProxyWorldManager::SyncLoadProxyWorldStream` (`0x824df648`) waits for the PROXY stream metadata, reads the XSS, stable-sorts its spatial rows by signed `tProxySort::mOrder`, inserts each sorted full ID into its membership map, calls `LoadCollection` with its load callback (`0x824dfa64..a88`), and waits for `mCollectionsLoaded == mNumProxyCollections` (`0x824dfab8`). `cLoadProxyWorldRequestCallback::OnComplete` (`0x824d68a8`) increments that same manager's loaded counter. `SyncActivateProxyWorld` (`0x824d9ef8`) first asserts loaded completion, sends two Presentation messages per sorted ID with a separate activation callback, then waits for `mCollectionsActivated`; `cProxyWorldActCallback::OnComplete` (`0x824d7d38`) increments that distinct counter. Parent-expanded requests and parent first-use messages are not substitutes for either counter.

`cLoadParentCollectionRequestCallback::OnComplete` (`0x82d5cac8`) forwards to `cAssetStreamManager::OnLoadParentComplete` (`0x82d5ca20`). The latter inserts/increments the parent use count and, only on first use, sends distinct Simulation and Presentation collection registration notifications at `0x82d5ca78` and `0x82d5caa4`, each with a `cParentCollectionLoadedCallback`. This is an effectful parent path, not a count-only callback. The current Rust `LoadParentCollectionCallback::complete_with` preserves the first-use order: resident Up, Simulation register, resident Up, Presentation register (`collection_parent_manager.rs:317..354`).

## Reusable Rust seam and actual blocker

The existing `StreamFile`, `WorldStreamCatalog`, `CollectionSpace`, `CollectionParentManager::plan_load`, `CatalogResidentCollectionLoadFactory`, `CollectionResidentStreamer`, and `OwnedResidentCollectionStorage<DecodedArenaAsset, ..>` supply the metadata, ancestor-first queue, physical decoding, and retained collection lifetime. A future root owner should hold one accepted PROXY catalog and one parent manager/streamer, enumerate **all** XSS rows, sort stably with `collection_stream_order` semantics, attach the manager's load callback only to each requested spatial leaf, and retain that same manager for later BAM high-collection membership. The current helper's `10_000 * x` can overflow in a debug Rust build, while the PPC arithmetic wraps; use an explicitly wrapping calculation when that production owner is implemented. The corpus XSS key sequence was not validated in this packet.

There is no production `CollectionParentEffects` implementation in current Rust. Its only implementations are the manager's tests, the Rob's Park observation probe, and the ignored census (whose effect methods are deliberately unreachable). There is no processed Presentation registry/product owner that can perform the parent Texture alias production and `RegArena` kind-0 shader `AddTexture` on that retained asset; the shader table is an unregistered, token-only draft. Spatial kind-2 mutable material binding and admitted kind-10 Environment registration are likewise missing. The renderer-bearing upload-client draft has no accepted PROXY root invoker and does not implement these effects. The `SelectedWorldStream` owner handles a later ordinary world stream, while the app's BAM probe and PROXY census release local diagnostic owners. Their observed 148 required collections, 147 spatial rows, and 93 parent Texture arenas are corpus facts, not enabled boot completion.

A standalone owner that increments 147 loaded callbacks while `presentation_register` returns success without processing/registration would make the parent path look complete and would let activation run against absent products. A source-ordered production patch therefore needs the retained Presentation processed asset and registration service (starting with the parent kind-0 alias and its matching shader manager identity), plus actual effect delivery and failure propagation. Only then can the owner honestly complete the enabled load gate; activation still requires the spatial kind-0/2/10 effects and separate activation callbacks before BAM starts. No owner patch is proposed here.

The smallest next native source question is the exact first parent single-Texture completion path: trace the `NotifyCollectionPresReg` message from `OnLoadParentComplete` through processed kind-0 `Presentation::RegArena`/shader `AddTexture` to its `cParentCollectionLoadedCallback`, including when its resident hold is released. That pins the first real effect/callback boundary for a bounded kind-0 producer using the existing decoded asset and GPU upload service. It does not require another parser or collection manager.
