# PROXY kind-0 Presentation owner boundary — standalone effect withdrawn (2026-09-23)

This amends the earlier unregistered kind-0 effect packet after independent review. The executable `apps/skate2-pc/src/proxy_kind0_parent_registration_draft_20260923.rs` was removed because its last-use logic was wrong for shared full arena IDs. No registered source was edited and no Cargo command was run. The earlier `artifacts/proxy-kind0-shader-table-public-boundary-2026-09-23.patch` remains an unapplied visibility proposal only; exporting the shader table does not make a valid owner or activate PROXY.

**Subsequent native finding:** `proxy-native-loaded-asset-canonicalization-shared-owner-2026-09-23.md` traces `cAssetManager::mLoadedAssetMap` and establishes that the native loader reuses one processed arena allocation for the same full asset ID across live collections in the same manager. The different-alias scenario below describes the **current host draft's** missing canonicalization, not the ordinary native load path. The standalone effect remains withdrawn because the host has no equivalent shared loaded-asset owner.

## Exact bug and source precedent

`PresThreadMsgMan::ReceiveRegCollectionMsg` (`0x82780958`) gates each processed arena's `Presentation::RegArena` through a Presentation-wide `cAssetRefCounter::AddAsset`. Kind 0 adds the processed alias pointer plus full TOC ID to `gTexMan` at `0x827f156c`. `ReceiveDRegCollectionMsg` (`0x8277fff8`) uses `RemAsset` and on last use calls `Presentation::DRegArena`; its kind-0 arm passes the **current processed arena's** alias pointer and TOC ID to `gTexMan.RemTexture` at `0x827f17bc`. The shader table's removal compares pointer identity. The separately queued load callback follows the registration effects; the later unload callback releases the Presentation resident hold. See `proxy-parent-pres-kind0-callback-hold-2026-09-23.md` and the shader-table source audit.

If parent A first registers arena ID X, its alias pointer is in the shader table. Parent B may then increment X's count without registering B's different alias. If A unloads first, B's later `RemAsset` reaches last use with B's pointer. The withdrawn draft looked up only B's resident asset, decremented X, and then rejected the shader-table pointer mismatch. Worse, it had no owner retaining A's boxed alias when A's resident collection was released. The table's identity token is a `NonNull` value, not a strong product owner. A parent-local effect taking borrowed `&mut ArenaRegistrationRefCounter` and `&mut ShaderTextureTable` cannot fix this by checking the last parent's resident view.

`PresentationDmoArenaRegistrationAdapter` is the source-backed host precedent. It owns one `ArenaRegistrationRefCounter`, a `live` collection-occurrence vector, and `first_use_owners: BTreeMap<u64, FirstUseOwner>` keyed by the **full** arena ID (`presentation_dmo_arena_adapter.rs:902..920`). It installs a live occurrence before the first manager call, and on each `FirstUse` retains a strong `Arc` of the exact prepared arena before dispatch (`:973..1025`). During last-use deregistration it dispatches using the current occurrence, removes the first-use ledger entry, and retains that first source in `orphaned_owners` when the current source differs and pointer-identity removal may not erase manager state (`:1448..1575`, `:1658..1704`). Its shared-ID test at `:3397` proves that the first source survives an earlier collection's deregistration. A separate kind-0 private counter or first-use ledger alongside this owner would split the native Presentation namespace.

## Smallest honest implementation boundary

The revised resident kind-0 builder currently stores a `Box<Kind0AliasProduct>` and decoded source inside each `Kind0ResidentArenaAsset`. `OwnedResidentAssetsView::try_for_each` gives a borrowed `&A` for the visit and discards its temporary `Arc<A>` snapshot afterward. It cannot transfer first-use ownership into a Presentation-wide ledger. A minimal unregistered producer revision would put the **same** alias and decoded source under one cloneable `Arc<Kind0ProcessedArena>` inside each resident asset, with alias-before-source field drop order preserved. Cloning that owner on `FirstUse` would retain the actual alias/GPU object and its checked source locators without reparsing or building a second texture inventory. A live occurrence would retain ordered `Arc` handles to those same processed arenas until its deregistration, mirroring the DMO adapter's `live` record.

One unified Presentation registration owner then needs the existing refcounter and existing shader table, a full-ID first-use owner ledger, live collection occurrences, and a fail-stop state. Registration must bind an occurrence to the accepted retained parent before iterating assets; `FirstUse` records the exact owner before `add_texture`. On last use it must use the current occurrence's product for the native `DRegArena` call. If that identity matches the first-use product, the shader table removes the same pointer before the unload callback releases its hold. If identities differ, native `RemTexture` can leave the first pointer in the table; safe host ownership must retain the first product as an orphan while that table entry remains, as the DMO adapter does. Silently removing A's pointer in place of B's would be a host policy change, not the recovered native call. Any such policy needs explicit review. Errors preserve the completed prefix and cannot acknowledge the queued callback.

The current `CollectionParentEffects` trait receives only `CollectionId` and returns delivery `Result<()>`; it does not itself resolve a resident processed container, transfer a live occurrence, or schedule the separate hold-releasing callback. `CollectionParentManager` already orders Simulation then Presentation notifications and resident Ups/Downs, but no concrete enabled-PROXY effect caller joins that manager to the retained kind-0 builder and unified Presentation registry. The next bounded production packet is the single unified owner plus that caller, not another parent-local effect. It must prove the accepted parent has all required processed products, use the same retained allocations for first-use insertion and last-use handling, and withhold callback success on any partial failure.

One native source question remains before choosing the shared-ID removal policy: does the processed container/arena registry canonicalize the same full arena ID across different parent collection occurrences, or can two live containers carry distinct alias allocations for that ID? Trace container registration and lookup around `mContainerAssetRegistry` as used by `ReceiveRegCollectionMsg`/`ReceiveDRegCollectionMsg`. The DMO host adapter handles distinct sources defensively, so the kind-0 owner must at least preserve that case until canonical identity is proved. This packet does not claim enabled PROXY boot.
