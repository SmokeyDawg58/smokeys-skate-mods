that mismatch as the reproduced cause of the historical crash.

## Confirmed host bug

The Rust Lua VM uses slab IDs for tables/functions/userdata. Cloning a `Value`
does not retain its target. Top-level `Lua::call` can perform mark-and-sweep when
the allocation counter reaches 8192, after resetting the call's stack top.
Its results were already explicitly rooted; that earlier fix remains.

`runtime::Delivery` previously held the message only as a Rust `Value`, and
`handle_message` held the activity's new data userdata only in Rust locals.
Neither was reachable by the collector once a top-level call returned.

Two concrete failing lifetime sequences follow directly from the source:

1. Message/data are created, then a first-use handler's **Attach** chunk crosses
   the collection threshold. GC can discard them before the handler is called.
2. One handler's return crosses the threshold. The next current/global-state
   handler or later subscriber reuses the discarded objects.

Access to an empty slab slot panics at `expect("live Lua object")`. If the slot
has been reused first, the stale handle can instead select a different object.
The allocation-dependent timing is compatible with an intermittent report,
but neither sequence was executed as a reproduction in this task.

## Repair and adjacent audit

- Retain the non-nil message in the existing Lua registry-reference mechanism
  until the entire local or routed delivery finishes. Nil messages allocate no
  reference. The shared table keeps its identity and handler-visible mutations.
- Retain both data and vars for the complete per-graph handler loop, covering
  lazy Attach, current/global handlers and ordinary Lua error returns. Release
  the temporary references once the graph finishes; release the message after
  the last recipient, matching the native ownership intervals.
- No changes to message order, state transitions, rewards, contest outcomes,
  physics, GC threshold or collection cadence.
- Document the host `Lua::call` rooting contract so future Rust callers do not
  treat cloned heap handles as owned Lua objects.
- Reviewed the other host call sites: objective vars are registry-backed;
  progression handler functions have registry references; global initialization
  does not keep transient Lua arguments across calls. Attribute userdata stores
  host collection keys rather than unmarked Lua handles. Nested native calls and
  metamethods run while depth prevents this between-call collection.
- Reviewed contest/results, progression termination, objective cleanup, Lua
  protected calls and the table collector for nearby panic/lifetime hazards.
  No additional contest-specific panic cause was established. This is not a
  complete VM parity certification or a campaign playthrough.

## PC diagnostics

The SIM worker holds the shared slot mutex while ticking. A Rust panic unwinds
that guard; ten lock/wait callers formerly replaced the cause with the generic
`SIM thread panicked` string.

The PC startup now installs a panic hook that captures the reason, source
location, thread and `Backtrace::force_capture()` **before unwinding**. It writes
a uniquely named, create-new report in `saves/crash_reports/` (or under
`SKATE2_SAVE_ROOT`), without requiring `RUST_BACKTRACE`. A SIM-specific summary
is retained before the mutex can become poisoned, and all ten error sites use
it. The original hook still runs. A file-write failure prints the report to
stderr even in quiet mode. No poisoned state is resumed.

This is a PC diagnostics improvement, not a claim of original-game behavior.
No report is written during normal play; there is no per-tick capture cost.
Missing symbols can limit backtrace symbolization. Abort/OOM/stack-overflow
failures that bypass Rust's panic hook are outside this reporting mechanism.
