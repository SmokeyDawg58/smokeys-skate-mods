# PROXY kind-0 render service and owner seam (2026-09-23)

Read-only Rust/source audit following `proxy-single-texture-alias-owner-audit-2026-09-23.md`. No registered module, executable draft, or Cargo command was changed. Confidence is high for the current Rust ownership and call order, high for the cited native registration order, and hypothesis for a future host GPU service composition. This note does not claim PROXY activation.

## What is concrete today

`DecodedArenaAsset` (`crates/skate2-core/src/assets/decoded_arena_asset.rs:48`) retains the full outer asset ID, XST resource descriptors, all five decoded resource buffers, and the parsed RW4 arena. `OwnedResidentCollectionStorage` stores each asset as an `Arc<A>` under its collection owner (`owned_resident_collection.rs:94, 509`), and `destroy` marks the collection dead before dropping its asset list (`:571`). Scoped `OwnedResidentAssetsView::try_for_each` can borrow the exact retained asset during a registration visit; it does not export a stable borrowed reference. `weak_assets_in_order` and exact-asset upgrade exist inside core but are crate-private (`:237, 311`).

`own_texture_arena` (`mounted_character_scene.rs:147`) already uses the parsed TOC, Texture, and GPU-buffer objects, and produces `NativeTexture` with the full TOC GUID, texture dictionary index, decoded levels, and copied encoded data. The serialized `Texture::parse` (`skate2-formats/src/material.rs:224`) has the six fetch words and an `ObjectId` for the GPU buffer; `Rw4Arena::local_entry` and `object_bytes` (`rw4.rs:240, 254`) resolve it against the retained resources. A future typed locator can therefore be the outer asset ID plus Texture dictionary index and GPU-buffer dictionary index/resource range, checked against that **same** retained `DecodedArenaAsset`. The serialized fetch address is an object reference; it is not the fixed-up Xbox pointer used by the native alias operation. No second parser is needed.

The real host upload service is `GpuRenderer::upload_native_texture(&NativeTexture) -> RenderResult<GpuTexture>` (`apps/skate2-pc/src/gpu_renderer.rs:323`). It validates source layout and device limits, rejects missing BC compression support, creates a `wgpu::Texture`, writes every decoded mip, and returns the owning `GpuTexture` (`:375`). This can be retained with a processed product. `create_textured_object` consumes a borrowed `GpuTexture` to build a bind group (`:290`). Current map inspection uploads during `RenderWindowClient::initialize` and keeps a local map of upload results (`render_inspection.rs:106, 143`); that diagnostic scene inventory is not the shader texture manager or a resident processed asset.

## Missing composition, so no product draft yet

The app render window creates `GpuRenderer` inside `run_with_options` immediately before invoking the client's `initialize` (`render_window.rs:44-45`). The existing resident texture builder's `StreamKind::Texture` arm stores only `DecodedArenaAsset` and telemetry (`robs_park_resident_probe.rs:473, 561`). Its `CollectionAssetBuilder::build` signature has no renderer argument (`resident_collection_load_driver.rs:171-188`). The other mounted texture path in `main.rs:12316-12325` creates a `TextureScene` from copied levels and drops the original decoded resource owner. Neither path produces a resident asset that holds the source arena, a distinct alias identity, and a `GpuTexture` together.

The minimum *composition* for a real kind-0 product is an app-owned PROXY resident asset built while the actual renderer service is available: it must retain the `DecodedArenaAsset`, a checked Texture/GPU-buffer locator, the source/aliased parameters and distinct stable alias identity, and the `GpuTexture` uploaded from `own_texture_arena`'s matching source texture. The builder must receive the actual `&GpuRenderer` from a renderer-bearing PROXY client or a concrete shared upload service. If streaming later occurs away from that callback, the owner needs an explicit upload queue and completion/failure latch before registration; a default, token-only, or deferred-success texture would fabricate the effect. Core cannot directly own the app's `GpuTexture` without moving a real service interface, so an app-level processed asset is the narrower first seam. The present repo has no production PROXY client or builder with that service, and no exact source-resource identity is preserved by `NativeTexture` alone. An isolated product module that assumes these inputs would be uncallable and would obscure this gap; none is proposed here.

## Ordering that integration must preserve

For each single-Texture arena, native `ProcessArena82d5fee0` makes the distinct alias header, registers its full TOC ID as Presentation kind 0, appends the product, then frees original lane 0 (`proxy-single-texture-alias-owner-audit-2026-09-23.md`). It does not free the alias allocation at that point. On Presentation arena first use, `RegArena827f155c..156c` calls shader `AddTexture` with that exact alias identity and TOC ID; `ArenaRegistrationRefCounter` in core already expresses the first-use decision. On last use, `DRegArena827f17ac..17bc` calls `RemTexture` with the same identity and ID before the alias/product can be destroyed. Unprocess removes registry entries and deletes the alias header/wrapper before release of the outer asset. Host GPU ownership must be dropped no earlier than manager removal. The native path retains original resource lanes 1-4 through its wrapper; a host product retaining the complete decoded arena is a conservative ownership bridge and must not claim the native lane-0 free timing is reproduced.

The existing unregistered `proxy_shader_texture_table_draft.rs` models manager table transitions only. It must receive a stable identity owned by the processed asset and must not itself create a texture. For PROXY, the 93 parent single-Texture products are only a subset of the observed 180 single-Texture occurrences; 87 spatial texture occurrences and material/Environment effects remain. Registration completion must follow real effect success. A successful upload or count of 93 products alone cannot acknowledge PROXY activation.

## Narrow next proof

Move one actual resident PROXY load under a renderer-bearing client or provide its builder the existing `GpuRenderer` through a concrete app service. In the same resident asset value, retain the decoded arena and owned upload, verify the TOC GUID and typed Texture/GPU-buffer locators against its arena, then publish one kind-0 entry. A focused real-corpus check should prove source locator validity, 93 parent products, exact full IDs, one upload per produced alias, failure propagation, first-use table insertion, last-use removal of the same identity, and collection unload only after removal. This is the smallest test that would justify an implementation draft; it still does not cover kind-2 material or kind-10 Environment activation.

## Renderer-bearing invocation audit

`main.rs:205-215` has one render entry, `--render-inspection`, which calls `render_inspection::run`. That function mounts the archives and builds separate Presentation/`TextureScene` inventories **before** calling `render_window::run_with_options` (`render_inspection.rs:17-93`). The window then creates `GpuRenderer` and calls `RenderWindowClient::initialize(&GpuRenderer)` (`render_window.rs:44-45`). This is a real, callable GPU handoff, but its client owns no `DecodedArenaAsset`/resident collection and its uploads are local inspection bindings.

The existing `SelectedResidentStartup` (`selected_resident_startup.rs:187`) is a reusable owner pattern, but its factory and registry are typed to `SimulationResidentArenaAsset`; it cannot load Presentation kind-0 products by passing another collection ID. The Rob's Park probe has a working catalog-backed factory and `CollectionResidentStreamer` (`robs_park_resident_probe.rs:2193-2217`), but its Texture builder retains only decoded arenas and its public `run` owns, checks, and unloads its diagnostic collections before returning. The PROXY census (`proxy_asset_census.rs`) directly uses the same mounted resident driver and `DecodedArenaAssetBuilder` for 148 required collections, but it is an ignored test with no app-facing owner. Neither is a collection client that a render window can retain.

The smallest callable route is therefore a **new app PROXY client** entered from `main` and passed to `run_with_options`; its `initialize` receives the actual `GpuRenderer`, starts or continues a supplied PROXY resident collection load through `CatalogResidentCollectionLoadFactory`, and retains the streamer/collection owner across frames. Its builder must be typed to a processed Presentation resident asset that contains both the exact `DecodedArenaAsset` and the GPU upload. A borrowed `&GpuRenderer` can be used during a synchronous `initialize` load only if the factory/streamer are released before return; that would also release their sole resident collection ownership. To stream or retain the owner across frames, the builder instead needs a concrete owned upload service extracted from `GpuRenderer` (or a carefully scoped callback each update) before it is stored in the streamer. `GpuRenderer` currently exposes only `upload_native_texture(&self)` and no cloneable upload service. The app's `RenderWindowClient::frame` receives a renderer borrow, so one possible narrower integration is to keep decoded assets in the resident owner and perform explicit upload/registration during a frame-scoped visit, storing owned `GpuTexture` beside that exact asset through a synchronized processed-state field. That choice needs a defined failure and deregistration path; it cannot treat an unuploaded asset as registered.

The PROXY metadata itself is currently loaded by the ignored census through `StreamFile`/`CollectionMap`/`AssetToc` and direct `WorldStreamCatalog` publication, whereas the app's completed outer BAM probe is self-contained and unloads its catalog after the optional resident probe (`main.rs:385-555`). `SelectedWorldStream` provides a retained outer-stream owner, but requires real supplied high-collection effects and a live texture cvar, and no PROXY render client currently constructs it. Moving its effectful PROXY load into the window is wider than a kind-0 product. Consequently this audit does not create a draft client that silently assumes an accepted PROXY catalog or a persistent GPU service. The next bounded integrator decision is whether the first renderer-bearing PROXY client receives a **preloaded, retained** accepted PROXY catalog and resident owner, or owns their loading and exact callback effects itself. Once that owner is concrete, the product builder is a small isolated step.
