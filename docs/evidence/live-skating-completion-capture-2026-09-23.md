The log proves frame-1 visual objects were prepared, not that they reached the display surface.

`--live-frames N` retains its existing meaning: N successfully presented window frames, including boot-only static-map redraws. That bound cannot reliably target selected frame 1. The patch adds `--live-completions N` as a separate positive bound, rejects using both bounds together, and allows `--live-capture PATH` with either bound. The new `RenderWindowClient::completion_bound_active()`, `completion_reached()` and `record_presented_completion()` default to inactive/no-op, so inspection and other clients retain their current behavior. In completion mode, capture is selected only after the live client reports N completed selected frames; the ordinary no-frame-limit first-redraw capture rule is not used. After `client.frame`, the window uses the existing `GpuRenderer::render_capture` on that same object list. Only after a successful nonzero-size present (and a completed capture write when requested) does the window record the presented-completion receipt and exit. With no capture path, it simply presents and exits. A run that closes after core/GPU completion but before actual presentation returns a clear prepared-versus-presented shortfall error.

The live client's accumulator can execute multiple 1/60 simulation ticks inside one redraw. It now breaks immediately after the requested completed tick and skips further ticks on redraw retries, retaining the map/skater GPU objects until presentation succeeds. This is necessary because the observed frame-2 pending action could otherwise fail before the renderer sees frame 1, even with completion-triggered capture. No second session, renderer, palette, material, camera or map constructor is added. A first-frame image remains a controlled diagnostic: static preloaded A_RobsPark map, source-selected character visual, provisional CameraMan projection and unlit shading. Native command-3/status, enabled PROXY activation and restored camera presentation remain pending.
