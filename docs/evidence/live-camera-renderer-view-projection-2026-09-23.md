# Native game-camera frame to render view, 2026-09-23

Read-only IDA and registered-owner audit for the first live visual frame. This is a **producer-to-render contract**, not a claim that the current app has the native presentation pipeline. No registered source or Cargo work was done. IDA addresses refer to the loaded original executable.

## Frame selection and update order

`Simulation::SimUpdate2` calls `CameraManager::Update` at `8289fc88`, then `WaitForUpdateToFinish` at `8289fcb0`. `CameraManager::Update82584448` calls `GameCameraManager::Update`, then obtains the first camera's `GetFrame`. `WaitForUpdateToFinish82582ef8` joins the game camera work and calls `UpdateChannels82582d68`. With `kbPickValidReplayCameraOnly` enabled (initializer `82f54030` defaults true), `UpdateChannels` copies `GameCameraManager::GetFrame` into channel frames. `CameraMan::GetFrame82e3b860` selects its ordinary `mFrame` unless `kbUsePhysOutCamera` is enabled (initializer `82fa22f8` defaults false). `CameraManager::GetCameraFrame82582c90` returns the selected channel frame for index zero, or the active static-camera frame; index >=1 asserts. These defaults are configurable and do not prove a particular mounted run's final settings.

`CameraPresentation::DoSimSubmit827f23a8` takes its count from `ICESceneBridge::IsCameraUsingSceneUp826c6d80`, whose loaded body returns one, then calls `CameraManager::GetCameraFrame` for index zero and copies that frame into the data provider (with a ghost-camera replacement branch). It reserves 16 local frames, but `GetCameraFrame` asserts for index >=1. `DoSimRestore827f60e0` makes `mInterpolatedData`: normal non-hard-cut frames use `CameraFrame::CameraFrame829d3e98(frameA, frameB, percent)`; a hard cut selects an endpoint. This constructor interpolates both current and previous matrices via `CameraFrame::Lerp`, plus FOV, near plane and other scalar/vector fields. `kSmoothDebugRendering` changes the path to a direct copy. `GetCurrentData826cb9e8` selects the current interpolated entry or shot/manual fallback. Thus the exact renderer camera at a draw depends on presentation submission/restore/selection and interpolation percent; a same-tick `CameraMan` snapshot alone is not necessarily the drawn frame.

`RenderMan::Render82858360` calls `UpdateCamera82848978` with jitter `0,0` before rendering the scene. Normal `CameraPresentation::GetMatrix827f6308` returns all four vectors of the selected frame's `mMatrix`. `UpdateCamera` computes a full affine inverse (adjugate/determinant reciprocal and translated origin in VMX), then passes that view to `ViewCamera::SetViewMatrix82825098`. A mere transpose assumes an orthonormal matrix and is not the native operation. `SetViewMatrix` copies the view and derives transposed/combined forms. The normal `GetMatrixPrevious82838d48` reads the selected frame's `mMatrixPrevious`; `PostFX::SetParameters_MotionBlur82846d38` consumes this getter at `82846d84`. It is not the view used for current scene geometry.

## Projection input distinction

`UpdateCamera` calls `GetFarPlane827f2630`, `GetNearPlane827ef8d8`, then `GetFOVY827f64b0`, converts the result with f32 degrees-to-radians constant `0.017453292`, and calls `ViewCamera::SetPerspectiveMatrixRadians82840770(fovyRadians, near, far, 0, 0)` at `82848b6c`. It obtains the presentation matrix a second time for frustum computation. The sources are:

| Value | Normal native source | Alternative branch / boundary |
|---|---|---|
| FOVY | `GetCurrentData()->mFOV` at frame `+0xc0` | Manual ICE/NIS flags return presentation `+0x10d0`; otherwise rendering-attribute layout pointer `Presentation+0xe48`, flag `+0x5a` can override with its `+0x60` value. Mounted override state was not established here. |
| Near | `Iris::kNearClipPlaneDistance.mTarget+0xd8` | Native initializer `82fa28a8` starts at 0.1 m, but runtime/config may change it. ICE returns presentation `+0x10d4`, NIS returns 0.8. `CameraFrame.mNearPlane` (`+0xcc`) is not read by this getter. |
| Far | rendering-attribute layout pointer at `Presentation+0xe48`, value `+0x64` | Its mounted/default numeric value remains unproven. |
| Aspect | hard-coded double `1.777777777777778` loaded at `8284080c` in `SetPerspectiveMatrixRadians` | No window width/height ratio or `CameraMan.aspect_ratio` is read by this projection function. The latter does enter lens-to-vertical-FOV computation. |

`CameraFrame` constructor `829d2ec8` sets `mFOV=60`, `mNearPlane=0.2`; Rust `camera_frame.rs` matches. `CameraMan::UpdateRig82e48344..5c` computes lens-derived vertical FOV using shot lens, medium size and `CameraMan+0x370` aspect, then stores it at `CameraMan+0x340`. That is Rust `CameraMan.vertical_field_of_view`. The audited UpdateRig tail writes `Frame.framing_x/y` at `82e48508/10` and `CameraMan::Update82e48a74` writes `Frame.near_plane` from the positioner. Neither write changes the renderer getter sources above. In particular, plugging `vertical_field_of_view` directly into the live projection would be an unsupported substitution.

With stereoscopy disabled and zero jitter, the scalar projection built at `828407e4..8284095c` has camera-column coefficients: `s = f32(fovyRadians * f32(0.63661975))`, `sx = -1 / f32(s * (16/9))`, `sy = 1/s`, `zz = far/(far-near)`, `wz = far*near/(near-far)`, and the perspective `zAxis.w=1`. The x scale is negative, y and forward z scales positive, and clip W comes from camera Z: positive camera Z is forward. The negative x scale makes camera-right project toward negative clip X. This is not the diagnostic tangent-based, viewport-aspect, negative-Z projection in `apps/skate2-pc/src/render_inspection.rs:260..304`. The native scalar path uses float/double conversions and can differ in final bits from an algebraically simplified host matrix; stereoscopy and jitter add separate branches.

## Smallest bounded app bridge

The retained Rust source is `CameraStartupFields.construction_state.camera_man: Option<Arc<Mutex<CameraMan>>>` (`camera_construction_probe.rs`), reached via the registered `SkaterObserverState::Camera` owner (`skater_manager_observers.rs`). `CameraMan` already retains `frame`, `physics_frame`, `vertical_field_of_view`, and `aspect_ratio`; `CameraFrame` retains current/previous `SkeletonRootMatrix`, FOV, near, hard cut and index override. `SkeletonRootMatrix::known_lanes()` only yields sixteen floats when every W lane is known; its columns otherwise preserve `Option<f32>` W. Existing `try_update_selected_prefix` runs the same owner's camera graph and CameraMan update. There is no public read-only frame accessor for the app, and `apps/skate2-pc/src/main.rs` only routes to the explicitly diagnostic `--render-inspection` path or probes; no live scene/presentation loop is present.

The bounded next bridge is a read-only, immutable **camera producer snapshot** taken under the existing camera-owner lock after a successful selected camera update: current and previous four-column matrices with known/unknown W preserved, frame FOV/near/hard-cut/index override, and an explicit ordinary-vs-phys-out selection flag. Expose it through the existing observer, then through a core public value type only when the app has a live caller. Keep it labeled producer data. A parity renderer requires a separate presentation stage that applies the native channel/static/ghost/manual choice and `DoSimRestore` interpolation, plus the mounted rendering-attribute far plane/FOV override and current near cvar, before constructing the inverse view and projection above. No renderer-visible numeric matrix can be claimed from the retained CameraMan alone.

The current `render_inspection` camera is deliberately excluded as a parity input: it derives eye from UI focus/distance, uses viewport aspect and tangent FOV, near/far 0.1/2000, and negative-Z clip convention. Its presence proves GPU plumbing only.
