## Exact owner path and source order

`SelectedSession::try_select_terrain` supplies the existing `SelectedSessionTerrain` with this boot owner's exact world `Arc`, asset `MountSet` Arc and cvars. `terrain_for(&world_arc)`/`ground_pool_for(&world_arc)` require that Arc identity and completed normal-arena registration. The draft does not load a second stream or decode/register an arena. The caller must complete `try_poll_stream`, `try_request`, and `try_poll` before camera admission; collection, unlock seed, arena userdata and DMO parallel answer remain explicit terrain inputs.

`try_admit_selected_camera_and_roster` requires the already constructed physical pair and completed terrain. It constructs this Actor's one-time physics auxiliaries **before** graph/camera/roster work, then ensures the existing player's graph owners, holds that session's world, obtains `SelectedTerrainStartup::try_camera_inputs` from its already admitted terrain/bounds and the same selected player owners, captures on the **existing** `SkaterManagerLocalIdentity` camera observer, then calls `SelectedPlayerStartupOwners::try_admit_first_actor` with that world's existing entity roster. The mounted branch captures camera and publishes the roster in `physical_player_ground_startup_corpus.rs:291-321`; its later auxiliary call was a fixture order and is deliberately moved earlier here. `actor_physics_auxiliary.rs:51-70` identifies its native Actor allocation at `0x825ff458..4ec`, after the physical constructor returns and before submittable/jobs. `try_admit_first_actor` publishes the Actor, loads Action/Motion graphs and finishes local observers in `selected_player_roster_startup.rs:23-39`. IDA `SkaterManager::SpawnPlayer 0x82600630` allocates the Actor/physical pair before `InitPlayer 0x826000b0` graph loading (see `selected-session-boot-owner-draft-2026-09-23.md`). The camera capability capture in between follows the already validated selected mounted branch; it does not claim the omitted whole native camera schedule.

`try_prepare_selected_queued_frame` first requires the boot owner's `presentation_complete` flag; `owners.presentation = Some` alone can be a partial field left by a failed startup. It constructs one `SelectedPresentationRuntime` from this player's retained `SelectedPresentationStartup` and its finalized mounted recipe scene, with caller-supplied `SelectedPresentationPolicy`. It retains one `SelectedPlayerTick` with an explicit selected-camera submit mask. The selected gravity is installed on the same world before physical body admission, as documented in `selected-prebody-gravity-2026-09-23.md`. Those are not fixture defaults: the current mounted corpus supplies LOD 0, capacity 65536, provider 0, root-W opaque bits 0, gravity parsed from Vault raw bytes and submit mask 3 in its own test context (`skater_presentation_frame_corpus.rs:22-34`, `physical_player_three_frame_corpus.rs:202-243`). The production host must choose and justify its values. The terrain owner has already constructed world-line queries before this preparation.

`try_with_selected_queued_frame` lends one borrowed `SelectedSessionFrame` from this session's retained world, board/skeleton, Actor, physical animation, input frame session, cvars/settings/services, presentation startup, selected tick and runtime; it also lends the same terrain ground pool and the **bound** `SelectedProductionInputOwner` queue/RNG. It creates no renderer, terrain, input platform, duplicate presentation runtime or duplicate `try_update`. The host performs pad poll/cache and pre-update enqueue with real loader/game-info/focus and supplies dt, physics/grind policy, numeric, sync, recognizer, feedback and observers. The registered `SelectedSessionFrame::try_step_queued` is the only tick/publication path: `NoCommands` returns before presentation; `Completed` binds materials after the tick if needed and publishes once through the retained runtime (`selected_session_frame.rs:83-185`). The 120/120 mounted queued/native-roster/camera corpus and 27/27 original baseline reported by root validate that lower path, but **do not** exercise this new cross-owner boot composition.

Camera and frame preparation are one-shot. A failure leaves the reached prefix in the existing session; a newly constructed presentation runtime remains retained if a later preparation step fails. There is no reset or retry that could repeat auxiliary allocation, roster insertion, graph load or presentation writes. The borrow method takes a world mutex guard only for the caller's frame closure, which must not re-lock that world; the caller supplies services before entry. This is a controlled host scheduling seam, not a native whole-frame scheduler.
