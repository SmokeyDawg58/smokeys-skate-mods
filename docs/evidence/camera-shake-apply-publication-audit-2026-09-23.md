# Camera shake Apply and frame publication: interruption handoff

Read-only IDA audit on 2026-09-23. This is a **partial source packet**, not an implementation approval. No registered Rust or Cargo was changed during this audit.

## Native owner and call boundary

`Iris::ShakeEffect::Apply(float dT,float subjectSpeed,float subjectDistance,Matrix44Affine const& mtx,bool activate)` is `0x82e43700..0x82e43cdc` (`?Apply@ShakeEffect@Iris@@QAA?AVMatrix44Affine@vpu@math@rw@@MMMABV3456@_N@Z`). Its actual PPC ABI uses r3=result pointer, r4=ShakeEffect this, f1=dT, f2=speed, f3=distance, r8=input matrix, r9=activate; raw `0x82e43724..44` copies these to r29, r30, f25, f26, f24, r28. The IDA prototype/decompiler have extra spurious arguments, so raw registers and the decorated symbol control interpretation.

Caller `CameraMan::UpdateRig` at `0x82e48714` branches on `shotEditor`. True copies Rig humanized matrix's X/Y/Z columns and positioner translation to `CameraMan::Frame.matrix` at `0x82e4871c..28`, then joins at `0x82e487ec`. False computes subject distance and calls Apply at `0x82e487a8`. It copies Apply's four returned matrix columns to `Frame.matrix` at `0x82e487ac..d0`, then copies `ShakeEffect.mShakeOffset` and calls `LogicalCameraPositioner::SetShakeOffset` at `0x82e487e8`. Thus the editor branch bypasses shake time, multiplier, output composition, and positioner shake offset publication.

After either path, `0x82e487ec..48854` writes `Frame.previous_matrix`: if `CameraMan +0x380` bit `0x40` or `Subject::GetHasTeleported` (vtable +0x178, actual getter at `0x82e3de00`, Subject +0x21d) is true, copy the just-published Frame.matrix; otherwise copy the old frame matrix saved in VMX registers v119/v118/v117/v120. Four full 16-byte columns, including W, are preserved. `SetShakeOffset` is an actual service and runs only on the non-editor branch.

## Apply source-order prefix and state writes

`ShakeEffect` PDB fields: +0x0 parameters pointer; +0x4 positions pointer; +0x8 rotations pointer; +0x10 shake offset vector; +0x20 keyframe count; +0x24 time; +0x28 one-shot effect; +0x2c multiplier; +0x30 wait-for-drop. Rust `CameraShake` already retains the corresponding owners in `camera_man.rs`.

`0x82e43748..68` loads old multiplier, uses literal 5.0 (`__real_40a00000`) and writes interim `old + dT*5` by `fmadds` when activate is nonzero, or `old - dT*5` by `fnmsubs` otherwise. `0x82e4377c..8c` then performs two `fsel` selections against 0 and 1 and overwrites multiplier with bounded result. Do not substitute ordinary Rust `clamp` without proving exceptional/NaN and signed-zero selection behavior. Both stores target `ShakeEffect +0x2c` (r30); decompiler aliasing to result matrix is incorrect.

`0x82e43790..c0` reads amplitude top speed +0x2f8, max +0x2f4, min +0x2f0 from GameCameraParameters. If top speed compares equal to zero (`fcmpu`/`beq`), amplitude stays min. Otherwise it divides speed by top speed, `fsel`-bounds the ratio, calls `Math::BezierLite::EvaluateYatX` on the embedded curve at parameters +0x0, then uses `fmadds` for `min + curve*(max-min)`. `0x82e437c4..e8` adds one-shot effect and multiplies by the just stored multiplier. `0x82e437d8..4380c` likewise reads frequency top +0x304, max +0x300, min +0x2fc and evaluates the distinct curve at parameters +0x40 when top != 0. `0x82e43810..20` overrides frequency with one-shot frequency +0x2e8 when `fcmpu(oneShot,0); ble` does **not** branch: this includes ordered positive and unordered/NaN, and excludes ordered nonpositive. Rust `CameraParameters` already exposes both curves and these scalar attributes as Options.

`0x82e43864..ac` reads ShakeDataFPS +0x308, subjectDistance, count +0x20, rotation array +0x8, position array +0x4; `0x82e438a8..ac` computes and stores `time += (ShakeDataFPS*frequency)*dT` with `fmadds`. The following vector phase/keyframe interpolation has not been fully lane-audited. A `divwu` by keyframe count occurs at `0x82e43924`; no prior zero-count guard was seen in raw Apply. Do not invent a default or silently skip the operation.

The later matrix composition writes four output columns at `0x82e43c88..94`. Raw output lane graph remains unaudited. After matrix output, `0x82e43c98..bc` reads one-shot decay +0x2ec, writes `(1-decay)*old_one_shot` to +0x28, and compares it against literal bits `0x3ba3d70a` (approximately 0.005) with `fcmpu; bge`. Ordered `>=` retains the product; ordered `<` and unordered/NaN overwrite +0x28 with +0.0 (`f30`). Exact W and exceptional matrix behavior still need proof.

## Further operand-level audit, still short of implementation

`Math::BezierLite::EvaluateYatX` is at `0x829b1e88`, reached by both calls `0x82e437b8` and `0x82e43804`. It initializes parameter `t=0.5`, evaluates `Math::BezierLite::Evaluate` (`0x829b0c60`) at least once, tests `abs(targetX-resultX)>0.01` and `abs(derivativeX)>2^-23` with `fcmpu/ble`, updates `t += (targetX-resultX)/derivativeX`, and caps at ten evaluations (`0x829b1f44..4c`). This separate scalar/VMX service is not present in the existing camera Rust owners. `Evaluate` consumes the actual four-column spline matrix and a `bezierBasisMat`; a generic cubic or linear substitute would not establish its FP/order behavior.

At `0x82e43870..e0`, subject distance contributes `(3.4f - distance) * 1.6666663f`, then an `fsel`-bounded scalar `f29` is staged. The phase path `0x82e438f0..43958` uses `vrfiz128`, `fctidz`, and `divwu` to choose `index = integer_phase % count` and `next = (index+1) % count`; the exact VMX subtraction order converting time to fractional phase is **not yet proven**. `0x82e4395c/64` load rotation and position keyframes at the current 16-byte stride, and `0x82e439c8/43a00` load the next pair. The source uses `count` as unsigned divisor without a zero guard before either `divwu`. Existing `ShakeKeyframes` represents both arrays and count, with incomplete positions/rotations possible after failed reads; a Rust continuation must retain partial state and cannot manufacture a frame for count zero.

`0x82e43968..88` reads parameter multipliers rotation +0x310, dutch +0x314, translation +0x30c. Interpolated rotation then feeds three distinct `XMVectorSinCos` calls at `0x82e43a84`, `0x82e43a94`, and `0x82e43aa4` for lanes 0, 1, 2. The resulting VMX graph constructs a scratch shake rotation at `0x82e43b68..bd4`, writes `ShakeEffect.mShakeOffset` +0x10 at `0x82e43bf4`, transforms it by the input matrix's first three columns (`0x82e43bec..43c04`) and overwrites +0x10 at `0x82e43c04`. This state is observable before one-shot decay. `0x82e43c08..94` composes the scratch transform with the input matrix and writes all four full-width output columns. Its operand map is: X=`v27` at `43c88`, Y=`v28` at `43c8c`, Z=`v26` at `43c90`, translation=`v25` at `43c94`; each uses the matrix columns, shuffle/constant vectors and `vmaddfp` terms at `43c28..84`. The special vector constant registers (`v64`, `v67`..`v70`, `v72`, `v77`, `v78`, `v83`, `v84`, `v87`, `v89`, `v93`..`v95`) and `vperm128` mask at `43b78` remain necessary to prove every XYZ/W lane. Do not replace this with a conventional affine compose: W terms and FP order are observable.

The direct editor path is separately bounded in raw `CameraMan::UpdateRig` instructions `0x82e48518..34` and `0x82e48714..2c`. `v123/v122/v121` load Rig humanized X/Y/Z and `v124` loads positioner position; `shotEditor` in r21 takes the direct branch, stores these four vectors to Frame.matrix in that order, then joins the hard-cut/teleport previous-matrix selection at `0x82e487ec`. It does **not** supply a normal-path substitute: the mounted first-skater camera call has `shotEditor=false`. An editor-only implementation could publish that mode, but cannot clear the live `PendingCameraSubjectSpeed` boundary.

## Stop and next audit

There is no source-backed complete Apply implementation here. Its first observable partial state write is multiplier +0x2c, then time +0x24, then output matrix, then one-shot +0x28. A safe eventual continuation should preserve this write order and partial-failure state, but the full phase interpolation, VMX rotation/output lanes, BezierLite implementation, and the `.shk` keyframe count contract need operand-level review first. The smallest currently defensible **full observable** segment is Apply plus caller Frame.matrix, SetShakeOffset, and Frame.previous_matrix publication; splitting before matrix output would leave the live frame path incomplete. Existing `CameraShake`, `CameraParameters`, and `ShakeKeyframes` are the Rust owners to reuse.

Prior input proof is in `docs/evidence/camera-shake-subject-inputs-source-2026-09-23.md`; its unregistered helper is `camera_shake_subject_inputs.rs`. This packet does not claim the helper is wired into the live camera path.
