# Flags3 Collision2 and adjacent assembly pair: source gap and contact relevance

2026-09-23 read-only audit of the matched `sk82_na_m.xex.i64` IDA/PDB, existing source packets, current Rust, and the adjusted-spawn Rust trace. **Exact** below means a native call, branch, store, or data flow observed in IDA at the cited address. **High** describes the typed interpretation of those operations. The first-two-tick implications are **conditional inference**: there is no matched native per-tick Contact/label/impulse capture for this spawn. No code or Cargo command was changed or run.

## Native order and owners

For the offline `FLAG_Both`/flags `3` simulation island, `World::Update1` (`0x827ae008`) calls simulation `Step_Update1` at `0x827ae150`, `Step_Collision1` at `0x827ae178`, then `Step_Collision2` at `0x827ae1a0`. `Step_Update1` (`0x827b2aa0`) begins the SkaterPool update. In `Step_Collision1` (`0x827b3818`):

1. `SkaterPool::EndUpdate` runs at `0x827b3838`, completing the full member publication before collision work.
2. The flags `3` branch asserts an **even** dense SkaterPool member count at `0x827b386c..3884`. It takes members at ordinals `(0,1)`, `(2,3)`, etc., orders each pair by unsigned native live `Assembly*` at `0x827b38f4..3914`, then appends its 16-byte `AlignedPair<Assembly const*, Assembly const*>` to `SimulationManager::mAssemblyPairs` at `0x827b391c..3958`. The atomic increment result minus one is the slot; an equality-at-capacity check restores the counter to the maximum instead of copying. `InitWorld` gives this World pair buffer capacity 500. The manager's buffer/counter/maximum fields are at `+0x60/+0x64/+0x68` (`assembly-island-partition-source.md`). The real first pair is the board then physical `SkeletonBody` in SkaterPool dense order; the board HookPool member is separate (`skeleton-body-producer-path.md`). Pointer ordering can reverse the pair endpoints and cannot be recovered from host object IDs.
3. If `kRunSkaterGroundCollisionPipeline` is true, `AssemblyGroundCollisionPipeline::Run` is submitted at `0x827b39ec` using the complete SkaterPool. **Correction, 2026-09-28:** flags `3` enters the later cvar-gated `SkaterDmo`, `SkaterSkater`, `SkaterPedestrian`, and `SkaterVehicle` assembly/assembly `Run` calls at `0x827b39f4..3a84`. The previous version of this note inverted that branch. Raw instructions `0x827b383c..3850` set `r27=0` for flags `3`; the `bne` at `0x827b39f4` therefore does not skip these calls. The adjacent board/Skeleton append itself performs no shape intersection and emits no `Contact`.

`Step_Collision2` (`0x827b2ab8..2ae8`) has only `if (mFlags != FLAG_Both && kRunSkaterGroundCollisionPipeline) SkaterGroundPipeline::Sync`. It therefore performs **no operation on flags `3`**. The comment in `skateboard_ground_frame.rs` saying flags3 Collision2 is a no-op is source-correct; the missing work is the preceding Collision1 pair append and the later full pipeline/partition schedule, not a Collision2 contact generator.

`Simulation::SimUpdate1` calls `World::Update1` at `0x8289f758`, then Predictor update at `0x8289f8f0`, StepSelector update at `0x8289f908`, locomotion at `0x8289f934`, and `World::Update2` at `0x8289f970`. Without a visual island, `World::Update2` calls simulation `Step_Collision3` (`0x827ae290`) then `Step_Solver2` (`0x827ae2a4`); with one, `World::Update1` submits simulation Collision3/Solver2 after both Collision2 calls (`0x827ae1d0/1e4`). On flags `3`, `Step_Collision3` (`0x827b4060`) sets `mMaxIslands=10`, populates the job tree, then conditionally **synchronizes** skater-ground first (`0x827b40fc..410c`) before its other pipeline syncs. Worker completion/Contact arrival order within the asynchronous Run is not established by these call sites.

`Step_Solver2` (`0x827b35b8`) calls single-player HookPool exclusion, normalizes active drives, optionally thaws, calls `SimulationManager::PartitionAssembliesInIslands` at `0x827b3698`, and creates simulation island tables at `0x827b36a8`. Partition (`0x82e0e2d0`) consumes the assembly-pair buffer in append order, makes a fresh map keyed by live Assembly pointer, and writes resulting signed labels to every Part body of each mapped Assembly. Its first unseen pair receives label `0`; further labels recycle at the ten-island cap. The pair buffer may also receive eligible pairs from other collision jobs, which append before contact intersection (`AssemblyAssemblyCollisionJob`, `0x827cc7b4..824` and `0x827cca04..4c`). Pair membership is therefore **not derivable from Contact rows**. The earlier `StartFrame` (`0x82e0bd80`) writes label `0` to Active bodies and `-1` to the static body; Solver2's HookPool exclusion writes `-1` to hook Parts. The exact partition and table rules are in `assembly-island-partition-source.md`.

## Current Rust and the bounded first-two-tick conclusion

This section records the September 23 implementation. For the September 28
pair-buffer, partition, DMO pipeline and adjacent skater-pair implementation,
see `dmo-assembly-collision-2026-09-28.md`; those changes remain uncompiled.

The retained Rust `SimulationSkaterAssemblyPool` already owns genuine board and Skeleton members and refreshes their publications in whole-pool phases (`dynamic_assembly_skater_pool.rs`; `skeleton-collision-and-mixed-pool.md`). `skateboard_ground_frame.rs::try_step_authored_ground` starts dynamic bodies/labels, refreshes both members, performs the Predictor harvest for its flags3 profile, excludes HookPool bodies, normalizes drives, snapshots labels, runs one synchronous authored Assembly/ground CPU job, prepares Contact/Joint/Drive rows, solves Horus, exports feedback, and builds physical contact lists. It has **no** source adjacent-pair append, pair-buffer partition, pipeline job submission/synchronization, or generic dynamic-pair job in this frame. `simulation_island_state.rs` implements the separate StartFrame and HookPool label stores; `simulation_island_map.rs` and the existing Contact/Jacobian consumers already represent the later label/table side. These are reuse points, not a second implementation request.

The **exact causal boundary** is that native flags3 terrain Contact production is launched by the skater-ground pipeline **after** pair append and is not performed by that append or Collision2. Thus the missing adjacent pair is not itself a missing board-ground narrow-phase test. If the controlled first two ticks have only the one board/Skeleton pair and the relevant Parts remain Active, StartFrame already labels those bodies `0`, and partition's first pair writes the same `0`; under those conditions omission of this pair alone does not remove board/terrain Contact rows from island `0`. This equivalence is an **inference**, not a verified state of the native two ticks. Frozen/non-Active Parts, additional dynamic pairs, recycled labels, or differing pipeline settings can invalidate it. Even when labels match, the isolated synchronous Rust job still has a real scheduling/coverage gap from native pipeline Run/Sync.

The adjusted-spawn Rust trace in `adjusted-spawn-board-fall-contact-audit-2026-09-23.md` shows board roll by frame 2, but lacks frame-1/2 ground-job row counts, per-Contact body/Part assignment and impulses, per-Part labels, and a matched native trace. It cannot establish that missing pairs caused the roll, that native first-two-tick Contact counts differ, or that the ground job produced zero rows. The useful discriminating capture is the existing selected tick's frames 1 and 2: report the ground-job `report`, Contact/Joint/Drive counts, selected Part labels, and each board/terrain Contact's body IDs, normal, and final normal impulse at the pre-solve and post-solve boundaries; correlate with board transform and the separate wheel-line/Body/Processed contact fields. A matched native capture at the same boundaries is required before a parity claim.
