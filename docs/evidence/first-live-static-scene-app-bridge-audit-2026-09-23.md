# First live static-scene app bridge audit, 2026-09-23

Read-only app/core/IDA audit. This packet is an implementation gate sequence, not a compilable app patch. No registered module or Cargo file was changed. Confidence is high for the present Rust ownership and app call sites; the native camera submit/restore facts below are direct IDA observations. A provisional producer-camera picture is not native camera-presentation parity, and the retained inspection scene is not PROXY activation.

## Reuse the existing owned paths

- `apps/skate2-pc/src/main.rs` already owns `mount_reference_archives`, `verify_world_stream_probe_identity`, `load_runtime_presentation_scene`, `load_runtime_texture_scene`, and `load_native_shader_manifests`. `render_inspection::run` uses these once for `A_RobsPark`, binds the resident textures, and builds one `NativeRenderQueue`. Do not add another map parser, asset loader, texture resolver, or render queue for the first visual test.
- `render_inspection.rs` retains `PresentationScene`, `TextureScene`, `NativeRenderQueue`, and a stable window-object vector. Its `initialize` uploads all static meshes; `frame` changes their clip matrices. `clip_from_mesh` deliberately leaves `defaultenvironment` vertices in world space and applies `submission.transform` for other effects. Preserve this explicitly diagnostic static scene path for the interim build, including its original-diffuse/solid-fallback reporting.
- `render_window::RenderWindowClient` already separates input events, object creation, and per-redraw work. `GpuRenderer` already uploads and renders both static meshes and selected character meshes. `selected_character_material.rs` maps the admitted actual effect name to the existing character GPU family, creates `(SelectedCharacterGpuBinding, GpuObject)` pairs, and updates them against the same `CharacterPalette` and `CharacterMaterialAdmission`. `gpu_renderer/character_palette.rs` rejects a foreign palette or swapped GPU object. No second window loop or renderer is needed. `selected_character_material.rs` is already registered at the end of `main.rs`, but has no production window caller.
- `windows_selected_input.rs` supplies `poll_and_cache` and `consume_sim` for the existing `SelectedDeviceInputEvents` trait and `WindowsPadPlatform`. It explicitly leaves the retained device-manager target, command queue, remap, focus, and full application schedule to the session owner.

## Core facade needed before the app patch can type-check

`selected_session_world_startup.rs` and `selected_session_player_startup.rs` are registered but `mod`-private in `skate2-core/src/lib.rs`. Their types and the selected physical/input/camera owners are `pub(crate)`. The candidate `selected_session_frame_draft_20260923.rs` is still unregistered, and its `SelectedSessionFrame` borrows already-created owners; it does not boot them. The selected physics/Actor/presentation composition currently runs in `#[cfg(test)]` corpus code. Consequently the app cannot import the selected tick or `SelectedPresentationRuntime` directly, and creating a nominal app `Session` by duplicating corpus startup would sidestep the ownership proof.

The smallest public boundary is one **opaque, retained core session**. Its boot entry should take the already mounted archive owner plus explicit host startup services and return either the first source-stage error or a single owner of world/local identity, selected Actor and physical pair, original-data terrain, input/queue/random, camera observer, presentation runtime, and material admission. The host supplies actual pad samples and timing; the core session retains the source service state. It should expose only a fallible `step` and a borrowed successful-frame view with `&CharacterPalette`, `&CharacterMaterialAdmission`, and the same observer's provisional `[f32; 16]` `clip_from_world` (or a named typed projection). A `NoCommands` result must not publish a new palette/frame. This is an API shape for root review, not evidence that `try_boot` exists or that all source-selected boot arguments are known.

`SelectedPlayerTick::try_step_queued` already orders delivered command recognition, selected Actor work, pre-solve, solver, post-solve, and optional selected camera subsequence. The unregistered frame draft then calls `SelectedPresentationRuntime::try_update` on the same Actor/services and checks `palette()` and `materials()`. That runtime publishes the palette only after produced, decoded, corrected, finalized and packed phases. Keep all these gates inside the core session; an app-visible frame may be borrowed only after success. The registered camera observer's `try_camera_producer_projection` also requires a completed selected camera update. Never synthesize an empty input target, camera matrix, pose, material, or PROXY result to make the facade return success.

The boot integration must lift the already verified corpus ownership in source order, using the registered selected world and player constructors, then the physical pair, world/terrain admission, actual pad/remap/command owner, camera capture, presentation/material owner and selected queued tick. `docs/evidence/selected-session-first-frame-seam-draft-2026-09-23.md` identifies outstanding thread/spawn selection, source-sampled world and query parameters, root-position W, and real pad/focus services. Each missing source capability should fail at its own boundary. The corpus currently chooses test spawn/thread and an explicit root-W transport; these cannot silently become production defaults.

## Minimal app connection after the facade exists

1. Keep the `--render-inspection` command and its scene loader intact. Add a separate, clearly labeled interactive first-skating command that uses the same static `A_RobsPark` scene construction and `RenderWindowClient`/`GpuRenderer` implementation. The static scene remains a visual backdrop; physics queries must come from the retained selected world/terrain owner, not from GPU meshes.
2. Boot one retained selected session from the same `MountSet` and its source-selected original data. Retain static GPU objects as the prefix of the window object vector. Store their count, corresponding queue submissions and colors, and a vector of selected character binding/index pairs.
3. On each OS event, feed the existing Windows pad adapter into the retained input target and queue actual mapped commands. Use a fixed simulation clock supplied by the selected session's validated scheduling policy; redraw cadence is presentation only. Do not advance simulation using `render_inspection`'s elapsed camera movement step.
4. For each successfully completed selected tick, borrow the session's same-frame palette/materials and provisional camera projection. Update each static object's clip with `clip_from_mesh(projection.clip_from_world, submission)`. On the first published palette, call `selected_character_material::create_objects`, append the returned GPU objects and save each binding with its stable object index. On later successful frames call `selected_character_material::update_object` with the same palette, matching object and current clip. No successful tick means no character publication. Keep errors visible; do not substitute a T-pose or solid skater.
5. State in the command/window caption and logs that the map is a retained inspection scene, shading and unresolved diffuse channels are diagnostic, and the camera is a provisional selected producer view. The selected player motion/input/palette may be live while this visual scene is static. Native PROXY streaming, material lighting, camera presentation restore, and full-frame Xenon parity remain separate work.

## Native camera evidence and remaining draw boundary

Direct IDA on `sk82_na_m.xex`: `CameraPresentation::DoSimSubmit827f23a8` calls `ICESceneBridge::IsCameraUsingSceneUp`, obtains selected `CameraManager::GetCameraFrame`, and submits counted `CameraFrame` data, with a ghost replacement branch. `DoSimRestore827f60e0` interpolates two submissions using the runtime percent; hard cuts choose an endpoint and the smooth-debug path copies. `RenderMan::UpdateCamera82848978` gets the current presentation matrix, computes a full affine inverse before `ViewCamera::SetViewMatrix`, then calls far, near, FOV getters in that order before `SetPerspectiveMatrixRadians`. Thus the registered `CameraProducerProjection` gives a useful interim view after a successful selected tick, but it is not the interpolated camera the original renderer necessarily drew. It also uses a provisional shared-Vault rendering-attribute proxy and approximate host math; its typed source translation W remains unknown on the mounted three-frame probe. Keep these labels attached to any app-visible first frame.
