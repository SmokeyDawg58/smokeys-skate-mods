The existing `skate2-formats` `MountedBig` and `AttributeVaultMetadata` parser, used by `artifacts/camera-render-attributes-probe-2026-09-23.rs`, resolves the class export at VLT `0x62c40` (layout size `0x78`) and its root/default collection at VLT `0x62eb8`. The class definitions corroborate byte `+0x5a` (key `4706e95acb6e90c4`, size 1), float `+0x60` (key `cbfc02f652423099`), and float `+0x64` (key `0d5d86ee00191acc`). The default collection's 13 explicit entries contain none of these three keys, so the parser resolves them from its layout payload. These are **mounted initial attribute data**, not constants to embed in the live renderer: the instance and layout can change, and getters read them at use time. The current registered `camera_attributes::BINDINGS[18]` already binds this rendering class/default collection as an `AttributeRuntimeInstance`, and `physical_player_assembly_corpus.rs` includes the class in its selected-class census. That binding proves the Vault service and class are reusable; native `CameraPresentation` constructs a **separate** instance at `+0xe44`, so a strict bridge should retain its own presentation instance rather than aliasing the camera-attribute object.

## Near plane

The mounted loose `data\startup.ini` has no `kNearClipPlaneDistance` line, so this initial value survives that startup deserialize. The existing retained `InputCvarReferences::try_camera_near_clip_distance()` reads live cvar index 330 (`input_cvar_camera_positioner.rs`), whose registered definition has the same 0.1 bits. The app must sample that reference at projection construction; the `CameraFrame.near_plane` or the rendering layout's own `+0x5c` 0.1 is not the normal getter's source. An external console or later runtime cvar write would change the value, so 0.1 is the mounted initial state, not a permanently fixed near plane.

## Normal freeroam submission and restore

`ICESceneBridge::IsCameraUsingSceneUp826c6d80` is a folded body returning **one**. Thus normal `CameraPresentation::DoSimSubmit827f23a8` submits a single `CameraManager::GetCameraFrame(index 0)` after the simulation camera update; it also has a player-ID-8 ghost replacement branch. The `kSmoothDebugRendering` initializer `82f6d628` defaults false. `GameModule::Update8273edc8` runs `SimController::Update2`, then `DataSysMan::SubmitFrame8277bca0`; that gathers simulation data when the returned flags include sim submission. Inside `Simulation::SimUpdate2`, `CameraManager::Update` at `8289fc88` precedes `WaitForUpdateToFinish` at `8289fcb0`, which copies game camera frames into channels. Therefore the submitted frame is from the completed camera tick, subject to the stated flags/branch conditions.

`GameModule::Render827320f0` checks in-game and restore permission, then calls `DataSysMan::StepTime8277c1d0` and `RestoreFrame8277f040` before `Presentation::Update827f7540` and `RenderMan::Render82858360`. `StepTime` calls the selected time controller's `Update`. In ordinary non-ghost realtime, `Presentation::EnterRealTime827f1130` constructs `RealTimeController` with normal update time `0.016666668` and sim restore flag. Its implementation constructor `82992848` starts `mFractionalFrameToRestore=1`, `mLastFractionalFrameToRestore=0`, `mUnAccounteddT=0`, and its last restored-frame identifier from `DataMan::GetLastFrameNumberWritten`. `RealTimeController::Implementation::Update82993f28` reads the latest written frame and the current sim rate from `Presentation::GetCurrentUpdateRate827f1120`, advances an accumulated real render `dT`, chooses a restorable frame with `DataMan::SkipForward`, and stores a fractional value. The raw `GetTickCount8298fd30` returns selected frame at impl `+0x0c`, fractional at `+0x10`, and normal/current-rate ratio from `+0x20/+0x24`. `DataSysMan::RestoreFrame` passes those to `DataMan::RestoreData82996580`, whose `InternalRestore82996090` selects two submitted frame buffers and passes the percent through `DataProvider::DoRestore82995ea8` to `PresentationObj<CameraPresentation>::Restore827f6828` and `DoSimRestore827f60e0`.

With normal non-hard-cut and debug smoothing false, `DoSimRestore` interpolates the two submitted frames using that percent. Its hard-cut branch uses an endpoint selected by restore direction; `kSmoothDebugRendering=true` copies an endpoint directly. The initial `1.0` in the controller constructor does **not** establish the first drawn frame's percent: `EnterRealTime` can occur before or after submitted frames, and `Update` changes both frame selection and fractional value based on actual render `dT`, current sim rate and available buffers. A numeric first-draw percent requires a captured original scheduler trace or exact host schedule inputs, including submit/restore flags and the first two frame identifiers. No fixed percent is justified by the static executable or mounted Vault.
