# PROXY kind-0 processed product owner and compiler seam (2026-09-23)

Read-only implementation audit following `proxy-parent-pres-kind0-callback-hold-2026-09-23.md`. The exact path was absent before writing. No registered Rust, unregistered executable draft, or Cargo command changed. Confidence is high for cited native control flow and current Rust signatures; a host representation of the fixed-up Xbox alias address remains a design choice, not exact ABI recovery. This note does not claim PROXY load or activation.

## Exact native product and first-use effect

`cProcessArenaAsset::ProcessArena` (`0x82d5fee0`) takes the single-Texture branch when the fixed-up TOC has count one and type Texture (`0x82d60058`). It samples source `Texture::GetParameters`, then calls `GetAliasedParameters` with that same source format (`0x82d600f8..0x82d60108`). `GetAliasedParameters` (`0x82bca760`) sets alias flag bit 0 and stores `this->Format.dword[1] & 0xfffff000` as `Parameters::address` (`0x82bca794..a4`). The width adjustment at `0x82bca7b8..cc` is skipped for this same-format caller. `GetResourceDescriptor` requests a distinct 0x34-byte lane-0 header, alignment 4, and zero-sized lanes 1..4 (`0x82d60114`). The Asset allocator creates the alias resource (`0x82d60168`), `Texture::Initialize` writes its header (`0x82d60180`), and `RegisterTexture` (`0x82d5ea00`) constructs a 0x1c `tGameTextureAsset`: aliased Texture pointer at +0 and +8, original resource bases 1..4 at +12..24, then a kind-0 Presentation registry entry and processed-list append (`0x82d5eabc..ac8`). `ProcessArena` frees original lane 0 after registration (`0x82d60228`), retaining the alias header and other source resource lanes. The outer container is published at `0x82d6048c`.

On parent first use, `PresThreadMsgMan::ReceiveRegCollectionMsg` (`0x82780958`) resolves that processed container, walks arenas forward, and gates each through `AddAsset` (`0x82780a3c`). `Presentation::RegArena` passes the processed wrapper's alias pointer and full TOC ID to shader `AddTexture` (`0x827f156c`). At last use `DRegArena` passes the **same** pointer and ID to `RemTexture` (`0x827f17bc`) before the processed product is released. The separate parent load callback does not release its resident hold; the deregistration completion does (`0x82d581bc`). A table entry keyed only by GUID, a decoded `NativeTexture` copy, or a GPU upload count is insufficient to represent this product/effect lifetime.

## What the existing Rust already provides

`DecodedArenaAsset` owns the full outer asset ID, XST descriptors, five decoded resource buffers and parsed RW4 arena. `own_texture_arena` walks existing TOC and Texture dictionary entries, resolves `Texture::data` to a GPU-buffer dictionary entry, and decodes all mip levels. `GpuRenderer::upload_native_texture(&NativeTexture)` performs a real device upload and returns an owning `GpuTexture`. `OwnedResidentCollectionStorage` and its scoped `OwnedResidentAssetsView` can retain and visit the **same** decoded allocation in authored collection order. `ArenaRegistrationRefCounter` supplies the first/last-use gate. The separately reviewed unregistered `proxy_shader_texture_table_draft.rs` implements shader AddTexture/RemTexture state transitions with full-ID normalization and stable identity tokens. These are the pieces to compose; another parser, resident manager, texture-scene inventory, or GUID-only table would duplicate or weaken existing owners.

A bounded host processed value would live inside the resident arena value and contain: the unchanged `DecodedArenaAsset`; full outer ID and full TOC texture ID; verified Texture and GPU-buffer dictionary/resource locators into that same arena; source and aliased parameter facts; a **distinct stable product allocation identity**; and the owned `GpuTexture` uploaded from that exact source. Its kind-0 registry entry would refer to that product, and the shader table would hold that product's stable identity. Removal must call the table with the same identity before the product and GPU texture drop. The host should model the native address as a checked source-resource locator plus real GPU allocation; a serialized fetch word is an ObjectId encoding and is not the fixed-up Xbox pointer stored in native `Parameters::address`. In particular, native reads the post-fixup fetch word at `0x82bca7a4`; current `Texture::parse` exposes serialized `fetch_words[1]`, not the native fixed-up address or the 0x34-byte Xbox header. That exact ABI field cannot be copied into a portable product without reconstructing the fixup/base allocation mapping, and must not be fabricated.

## Current compilation/callback block

The retained `CollectionAssetBuilder::build` receives asset metadata and bytes, not `GpuRenderer` or an owned upload service. `RenderWindowClient::initialize` and `frame` receive only `&GpuRenderer`; `GpuRenderer` owns its `wgpu::Device` and `wgpu::Queue` privately and exposes only borrowed `upload_native_texture(&self)`. A factory retained inside `CollectionResidentStreamer` cannot hold that window callback borrow across frames. The existing unregistered `ProxyTextureResidentClient` works around this by loading with a local direct driver, then visiting and uploading after load; it has no parent callback, processed registry, or shader insertion. Moving its upload after a real parent callback would put native first-use registration before product construction. Its visitation also has a known `Box<dyn Error>` conversion compile blocker from the independent review. The shader table draft is unregistered and crate-private inside core; an app product cannot call it through the current public API. These are concrete Rust composition gaps, not a reason to make a second table.

Therefore an isolated product file cannot yet prove the **full** requested effect from resident construction through first-use callback and removal. I did not author an uncallable or success-only patch. The smallest production seam is to give the existing resident builder an owned, renderer-backed upload capability with a defined error/lifetime boundary, then store processed kind-0 state inside its resident asset before physical load completion. Register or expose the already reviewed shader table once, and connect an owner-bound Presentation registry that resolves the same resident collection for ordered first/last-use visits. A focused mounted test should check all 93 parent products and full IDs, exact Texture/GPU-buffer locator agreement, one real upload per product, insertion before the parent callback, and same-identity removal before the two external resident holds are released. A failed upload or registration must retain its completed prefix and must not acknowledge the callback. Spatial kind-2/10 effects remain separately required for PROXY activation.
